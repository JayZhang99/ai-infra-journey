## 三、理论学习与闭卷结果

### 3.1 已掌握内容

- persistent Buffer 会进入 state_dict，并随 Module 迁移 device/dtype；通常由模型逻辑更新，不由 optimizer.step() 更新。
- grad_fn 表示产生非叶子 Tensor 的反向节点；.grad 是累积梯度缓冲区。
- CUDA Python 返回通常只表示 Kernel launch 已提交，不代表 GPU 已完成。
- 同一 Stream 内按顺序执行；跨 Stream 的依赖需要 Event、wait_event 或 wait_stream 等显式协调。
- 同步墙钟用于观察主机端约定边界，CUDA Event 用于测量同一 CUDA 时间线中 Event 之间的工作。
- .item()、.cpu() 和 synchronize() 可能引入同步并破坏流水。
- compute-only 与 H2D+compute 的测量边界不同，不能直接混用。
- Benchmark 用来给出约定边界下的 latency/throughput；Profiler 用来定位时间花在哪里。
- HVP 避免显式构造 O(N²) Hessian，只保留向量规模的输入输出，因而更可扩展。

### 3.2 仍错误或不完整的知识点

1. **non-leaf 保留梯度接口**

   错误写成了 retained_grad。正确接口是：

   ```python
   tensor.retain_grad()
   ```

2. **retain_graph 与梯度累积混淆**

   retain_graph=True 的职责是保留本次 forward 构建的计算图，使同一张图可以再次 backward 或 autograd.grad；它本身不负责 .grad 累积。

3. **非标量 backward 的 gradient**

   gradient 不是“微分矩阵”，而是与输出同 shape 的上游梯度向量 v，计算的是 VJP：

   ```text
   vᵀJ
   ```

4. **MatMul FLOPs 算错**

   ```text
   2 × 512³
   = 268,435,456 FLOPs
   ≈ 2.68 × 10⁸ FLOPs
   ```

5. **pinned memory 解释不准确**

   pinned memory 是不会被操作系统换出的 page-locked CPU 内存，可支持更直接的 DMA 传输；它不是“只给 GPU 使用的内存”。

6. **CUDA Event 边界过度简化**

   Event 不一定只测 Kernel。它测量两个 Event 之间排入相应 CUDA 时间线的工作；区间内也可能包含异步拷贝。

7. **non_blocking=True 条件回答不完整**

   non_blocking=True 不保证 copy/compute overlap。还要检查 pinned source、不同 Stream、数据依赖、同步点以及硬件并发能力。

8. **Profiler 不能代替 Benchmark 的原因不完整**

   Profiler 存在采集开销，聚合表也不等同于约定边界的端到端分布；最终 latency 仍应以独立 Benchmark 为准。

### 3.3 理论补测题

- retain_grad()、retain_graph 和 create_graph 分别解决什么问题？
- 非标量 backward 的 gradient 为什么是 VJP 的向量？
- 2 × 512³ 等于多少 FLOPs？
- pinned memory + non_blocking=True 为什么仍不保证 overlap？
- Self time、Total time 和最终 Benchmark latency 为什么不能混用？

补测验收线：**至少 8/10，且 FLOPs、VJP、pinned memory 三题不得再错。**

## 六、CPU/CUDA Benchmark 实测

| Size | CPU median | CPU p95 | CUDA median | CUDA p95 | CPU/CUDA speedup |
|---:|---:|---:|---:|---:|---:|
| 128 | 0.005167 ms | 0.005586 ms | 0.104384 ms | 0.139426 ms | 0.05× |
| 512 | 0.133334 ms | 0.202229 ms | 0.103056 ms | 0.135528 ms | 1.29× |
| 1024 | 1.449334 ms | 1.882006 ms | 0.173056 ms | 0.204126 ms | 8.37× |

实测解释：

- size=128 时 CPU 约快 20.2×。
- size=512 时 CUDA 约快 1.29×。
- size=1024 时 CUDA 约快 8.37×。
- 加速比随规模增大明显上升。

限制：CPU 数据来自 Mac ARM，CUDA 数据来自 WSL RTX 4070 Ti。这是跨机器整体比较，不能严格归因于 CPU/CUDA 后端差异。公平对比需要在同一 WSL、同一 PyTorch 版本和同一提交上重新运行 CPU 网格。

## 七、Profiler 观察事实

### 7.1 CPU

- 512×512 float32 MatMul 最终落到 aten::mm。
- aten::mm 共调用 10 次，Self CPU 合计约 1.917 ms，Top 5 中占 67.27%。
- 第一次 CPU aten::mm 约 494.7 us，后续大部分约 130～239 us。
- Profiler 中 aten::mm 平均约 192.1 us，高于独立 Benchmark median 133.3 us，因此 Profiler 时间不作为最终 latency。
- 10 次输出累计记录约 10 MB 分配；单个 512×512 float32 输出约 1 MB。

### 7.2 CUDA

- aten::matmul 最终落到 aten::mm。
- 每次 MatMul 产生一个 CUTLASS SGEMM Kernel 和一个 splitKreduce Kernel。
- 10 次调用的底层 CUDA Kernel 忙碌时间合计约 217.676 us，平均约 21.77 us。
- CUTLASS 主 Kernel 平均约 17.89 us，splitKreduce 平均约 3.88 us。
- Kernel 位于同一个 CUDA Stream，没有 Kernel overlap。
- Trace 中没有 H2D copy，当前边界是 compute-only。
- matmul_compute_only 的 Self CUDA 百分比超过 100%，原因是外层 record_function 与内层 aten::mm 对同一批 Kernel 存在嵌套归属，不能把这些百分比相加。
- Trace 末尾存在一次约 493 us 的 cudaDeviceSynchronize，它属于 Profiler 收尾等待，不是每次 MatMul 的 Kernel latency。
- Profiler 存在约 2.947 ms 的 Activity Buffer Request。
- 第一次 CUDA 侧 aten::mm 的 CPU 调用约 3.095 ms，后续约 20～67 us。
- Trace 中存在约 82 us 和 385 us 的 GPU 空隙。

## 八、性能假设与验证计划

### 假设 H1：Profiler 初始化污染了第一条样本

依据：

- 第一次 CUDA 侧 aten::mm CPU 时间约 3.095 ms。
- 后续调用只有约 20～67 us。
- 同期存在 Activity Buffer Request。

验证：

- 使用 Profiler schedule 增加 wait/warmup/active 阶段。
- 不把第一个 Profiler step 纳入 active 区间。
- 对比重采后的 Top 5 和 trace。

状态：**pending**。

### 假设 H2：部分 GPU 空隙来自 Profiler/CUPTI 或 WSL 调度

依据：

- GPU 出现较长空隙时，CPU 仍在提交后续 Kernel。
- 当前证据不支持直接断言“CPU 没有及时供给 GPU”。

验证：

- 关闭 record_shapes 和 profile_memory 后重新采集。
- 将 active steps 从 10 增加到 100。
- 对比空隙出现频率和位置。

状态：**pending**。

### 假设 H3：小矩阵受固定启动和调度开销主导

依据：

- size=128 时 CUDA 明显慢于 CPU。
- size=512 时 CUDA 只有约 1.29× 加速。
- size=1024 时 CUDA 达到约 8.37× 加速。

验证：

- 增加 2048、4096 两档规模。
- 在同一 WSL 环境重新测量 CPU 和 CUDA。
- 检查加速比是否继续随规模增长。

状态：**pending**。

### 假设 H4：当前 MatMul 边界包含输出分配影响

依据：

- 每次 torch.matmul 都返回新的输出 Tensor。
- Profiler 记录了 10 次调用累计约 10 MB 输出分配。

验证：

- 增加预分配 output + out= 的独立实验。
- 明确命名为 matmul_preallocated_out，不能与当前边界混写。
- 比较 CPU self time、CUDA Kernel 和正式 Benchmark。

状态：**pending**。
