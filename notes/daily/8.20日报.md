### 2.3 错题订正

#### Runtime 与 Serving

- Runtime：加载模型、选择/优化执行图、调度算子或 Kernel，并在具体设备上执行推理。
- Serving：管理网络协议、序列化、请求队列、动态批处理、超时、限流、错误处理和监控。
- 边界：Runtime 关注“模型怎样被执行”，Serving 关注“请求怎样安全、稳定、高效地进入 Runtime 并返回结果”。

#### Concurrency、Queue Time 与 p99

- Concurrency 是系统中尚未完成的请求数，包括正在排队和正在执行的请求，不等同于积压请求数。
- 当并发超过系统可持续处理能力时，请求更容易等待，Queue Time 和 p99 通常上升。
- Queue Time 上升而 Compute Time 基本不变，说明单次模型计算没有明显变慢，瓶颈更可能位于容量、调度、批处理等待或上游突发流量；仅凭这两个指标不能确定唯一根因。

#### 有界队列解决的问题

1. 限制队列占用的内存和请求上下文资源，避免无限增长。
2. 限制最长等待和尾延迟，避免请求长时间无意义地滞留。
3. 在过载时提供明确的拒绝、超时或降级策略。
4. 向上游形成背压，保护 Runtime、GPU 和下游服务不被流量压垮。
5. 提供可观测的容量边界，便于围绕队列深度、拒绝数和等待时间报警。

#### Parameter 与普通 Tensor

- 核心区别不是“Parameter 会变化、普通 Tensor 不会变化”，而是注册语义。
- `Parameter` 赋给 `nn.Module` 属性后会被自动注册，出现在 `model.parameters()` 和 `state_dict()` 中，优化器通常据此获取可训练权重。
- 普通 Tensor 也可以变化、也可以设置 `requires_grad=True`，但不会仅因为被赋给 Module 属性就自动成为模型参数。

#### `state_dict`

- 模型的 `state_dict` 包含 Parameter 和持久化 Buffer，例如 BatchNorm 的运行均值与方差。
- 它不包含模型类、`forward()` 逻辑、Python 源码或运行环境，也不自动包含优化器状态。
- 恢复时必须先构造兼容的模型结构，再调用 `load_state_dict()`。

#### `eval()`、`no_grad()` 与 `inference_mode()`

- `model.eval()` 只切换训练/推理行为，主要影响 Dropout、BatchNorm 等模块，不会自动关闭梯度记录。
- `torch.no_grad()` 与 `torch.inference_mode()` 都能关闭推理阶段的 Autograd 记录。
- `inference_mode()` 进一步减少版本计数和视图跟踪开销，限制也更严格；纯推理优先使用它，需要与 Autograd 交互时使用 `no_grad()` 更灵活。

#### 保存加载如何验收

1. 固定随机种子和输入。
2. 保存训练后模型的 `state_dict`。
3. 构造相同结构的新模型并加载权重。
4. 两个模型都切换到 `eval()`，在 `inference_mode()` 中对同一输入推理。
5. 比较输出最大绝对误差，并设置明确标准，例如 `< 1e-6`。

首次编译在列表初始化处报错：

```text
error: expected ';' at end of declaration
const std::vector<int> values{1, 2, 3, 4};
```

根因不是 C++ 代码缺少分号，而是 CMake 没有真正启用 C++20：

- `set(CMAKE_CXX_STANDARD)` 缺少版本号。
- `CMAKE_CXX_ENTENSIONS` 拼写错误，应为 `CMAKE_CXX_EXTENSIONS`。

修复后的配置为：

```cmake
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

### 5.3 WSL/CUDA 故障与复核

首次运行 MLP CUDA smoke 时出现：

```text
RuntimeError: Expected all tensors to be on the same device,
but got mat1 is on cpu, different from other tensors on cuda:0
```

根因：`model.to(device)` 会原地修改模型并返回同一个对象。执行 `cuda_model = model.to(device)` 后，`model` 和 `cuda_model` 指向同一个 CUDA 模型；随后再用 CPU 的 `x` 调用 `train_model(model, x, target)` 就会触发 device mismatch。

同时需要订正两点：

- `train_model()` 返回 `list[float]`，不能调用 `cuda_losses.cpu()`。
- GPU 最终 Loss 不保证严格小于 CPU 最终 Loss；CUDA smoke 应验证模型与输入位于同一 CUDA 设备、训练能够完成且 Loss 下降。

## 六、三个以上新认识

1. CUDA 可用不等于代码自动使用 CUDA；模型、输入、标签以及新增 Tensor 必须位于兼容设备。
2. `Module.to(device)` 会原地修改 Module，并返回同一个对象；给返回值换一个变量名不会复制出独立模型。
3. `model.eval()` 管理模块行为，`inference_mode()`/`no_grad()` 管理 Autograd，二者职责不同且推理时通常要配合使用。
4. `Parameter` 的关键是注册语义，而不是“是否会变化”；优化器只能更新实际传给它的参数。
5. 测试数量不等于测试质量：没有断言的测试会假通过，CUDA 测试也不能用“GPU Loss 必须比 CPU 更低”作为验收条件。
6. 构建错误出现于 C++ 源码行，不代表根因一定在源码；需要查看 CMake 配置和实际编译参数，例如是否存在 `-std=c++20`。
