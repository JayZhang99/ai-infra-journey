- 能识别 `ddevice` 拼写错误和整数 Tensor 会让 device mismatch 测试在目标检查之前失败。
- 能把“Full gap p95 更大”写成 Observation，而没有直接当作最终因果结论。

### 必须订正

1. **Pinned Memory 不是 Host Memory 的同义词。**

   Pageable 与 Pinned 都属于 Host Memory。Pageable 页面可能被操作系统换出；Pinned 页面被锁在物理内存中，更适合 DMA，并且是可靠发起异步 H2D 的关键条件之一。

2. **`non_blocking=True` 不等于传输完成，也不保证一定发生重叠。**

   它只改变提交和等待行为。能否重叠还取决于 Pinned Memory、不同 Stream、正确的数据依赖、可用 Copy Engine、资源竞争和任务规模。

3. **Cached/Full 必须比较同一个语义位置。**

   正确比较对象是 `cached_output` 与 `full_output[:, -1:, :]`，而不是 cached 输出与完整 full 输出；Attention 返回 `(output, weights)`，浮点结果使用 `torch.testing.assert_close`。

   ```python
   full_output, _ = scaled_dot_product_attention(q, k, v, mask)
   cached_output, _ = scaled_dot_product_attention(q[:, -1:, :], k, v)

   torch.testing.assert_close(
       cached_output,
       full_output[:, -1:, :],
   )
   ```

4. **`.item()` 不是规范的 H2D 计时修复方法。**

   `.item()` 可能触发同步，但会把取值操作混入边界。GPU copy-only 时间应使用 CUDA Event；CPU 端端到端时间应在边界前后调用 `torch.cuda.synchronize()`。

5. **Full/Light 唯一改变的参数必须能准确写出。**

   当前实现中 Full 开启、Light 关闭的是：

   ```python
   record_shapes
   profile_memory
   ```

   输入、设备、dtype、warmup、steps、Profiler schedule、同步边界和输出处理均应保持一致。

## 六、Full/Light Trace 分析

### 实验边界

- 矩阵：`[512,512] @ [512,512]`
- dtype：`float32`
- 有效 MatMul 调用：10 次
- 每次 MatMul 对应 2 个 CUDA kernel，共 20 个 kernel
- 两份 trace 均没有 Memcpy/H2D 事件
- 因此当前实验只能解释 **compute-only Profiler 行为**，不能回答 H2D 或 pipeline overlap

### 数据对比

| 指标 | Full | Light | 观察 |
|---|---:|---:|---|
| Kernel 数量 | 20 | 20 | 一致 |
| Kernel 总时间 | 216.805 us | 212.010 us | Full 高约 2.3%，计算本体接近 |
| First-to-last envelope | 809.394 us | 624.165 us | Full 高约 29.7% |
| Envelope busy ratio | 26.79% | 33.97% | Full 的空隙占比更高 |
| Gap median | 1.283 us | 1.174 us | 小 gap 接近 |
| Gap p95 | 205.267 us | 169.993 us | Full 高约 20.8% |
| Gap max | 205.267 us | 169.993 us | Full 更高 |
| 大于 10 us 的 gap 数 | 5 | 3 | Full 更多 |

### Observation

- Full 与 Light 都执行 10 次 MatMul、20 个 kernel，kernel 模式相同。
- 两者 kernel 总时间只相差约 2.3%，说明 GPU 计算本体没有出现同量级变化。
- Full 的 envelope、gap p95 和大 gap 数量都高于 Light，差异主要出现在 kernel 之间的空隙，而不是 kernel 执行总时长。

### Hypothesis

`record_shapes=True` 和 `profile_memory=True` 带来的额外采集工作，**可能**影响 CPU 提交节奏或 Profiler/CUPTI 记录路径，从而扩大部分 kernel gap。

这只是候选解释。当前只有一组 Full 和一组 Light，不能排除 WSL 调度抖动、后台负载、CUDA 库内部策略或偶然长尾，因此不能写成“Full 采集一定导致 gap”。

### 下一步验证

1. 固定硬件、进程、size、dtype、warmup、steps、schedule 和同步边界。
2. Full/Light 交替运行，每种至少 10 轮，避免固定先后顺序带来的偏差。
3. 每轮分别统计 kernel 数、kernel 总时间、envelope、gap median/p95/max 和大 gap 数。
4. 同时保留独立 CUDA Event benchmark；Profiler trace 用于解释结构，Event 用于判断真实性能。
5. 如果多轮中 Full 的 gap 分布仍稳定右移，才支持“额外采集开销影响提交间隙”的假设。
