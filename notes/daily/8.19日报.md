### 推理与性能指标闭卷

- 部分得分：`6/10`。
- 严格完整题数：`4/10`。
- 结果：未达到 `8/10` 验收线。
- 已掌握较好：动态批处理需要最大等待时间；性能报告需要记录硬件、软件、shape、dtype 和 Batch Size。
- 仍错误或不完整：
  1. Runtime 描述过窄；应包括加载、优化和执行模型、选择后端/Kernel、管理输入输出 Tensor。
  2. Operator/Kernel 没有给出具体例子；一个 Operator 可选择多个候选 Kernel，多个 Operator 也可融合成一个 Kernel。
  3. Latency 应定义为一次请求所需时间；Throughput 是单位时间完成的工作量。
  4. 忘记 Concurrency：它是同一时刻处于等待或执行状态的未完成请求数；过载后会增加 Queue Time 和 p99。
  5. 平均延迟不能表达 p95/p99 所反映的长尾。
  6. Queue Time 上升但 Compute 不变，说明模型计算稳定、执行前等待增加；不能据此认定 Batch Wait 或 Serialization 变慢。
  7. 有界队列至少承担限制内存、限制等待、触发拒绝/背压、防止过期请求浪费 GPU 和保护恢复能力。
  8. 正确全称：TTFT=`Time To First Token`，TPOT=`Time Per Output Token`，ITL=`Inter-Token Latency`。

## 代码复核发现的问题

1. `reduction_and_matmul_demo()` 中 `reduced_mean = x.mean(dim=1)`，但返回键名为 `mean_last_dim`；命名与实际计算维度不一致。应改成 `x.mean(dim=-1)`，或把键名改为 `mean_dim_1`。
2. 当前测试没有导入和直接调用 `reduction_and_matmul_demo()`；现有 Reduction/MatMul 测试重复写了 PyTorch 运算，因此即使该辅助函数写错，测试仍可能通过。需要增加对函数返回值的直接测试。
3. `view_eroor` 是拼写错误，虽然最终通过 `view_error` 键返回、不影响当前行为，但应改为 `view_error`。
4. `tensor_nbytes()` 的 Docstring 写成 storage size，更准确应写 logical bytes for a dense tensor，避免与 View 的底层 Storage 混淆。
5. 代码格式存在少量空格和函数间空行不一致，后续可使用 Ruff/Black 统一，但不影响今天功能验收。

## 三个新认识

1. Tensor 由 Storage 与 shape、stride、dtype、device、offset 等元信息共同定义；仅看 shape 不足以理解内存布局。
